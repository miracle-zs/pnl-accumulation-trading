# 15 分钟定时交易系统：精简架构

本文只描述 PRD 所需的最小系统：一个常驻进程，每 15 分钟读取账户和行情，按固定策略决策，执行订单并保存状态。

## 1. 总体结构

```text
15 分钟调度器
      │
      ▼
巡检流程 ─── 策略规则
   │              │
   ├── 交易所 REST 接口
   │      ├── 仓位、价格、合约规则
   │      └── 市价下单、订单和成交查询
   │
   └── SQLite
          ├── 标的状态
          ├── 订单意图
          ├── 已确认成交
          └── 看板采样与未解决异常

可选：告警与日报
```

部署为单进程、单账户、单实例。程序以 REST 轮询为主，状态保存在本机 SQLite。

## 2. 模块

| 模块 | 工作内容 |
| --- | --- |
| 调度器 | 在每个 15 分钟整刻启动一轮巡检 |
| 巡检流程 | 每轮先恢复未完成订单，再读取本轮账户与标的快照，按优先级完整处理候选标的 |
| 策略规则 | 根据 Tier、收益率、批次状态和标的资格，返回一个动作或持有 |
| 交易所接口 | 获取持仓、标的目录、全市场最新价和合约规则；提交市价单；查询订单与成交 |
| SQLite | 保存标的状态和订单执行事实 |
| 巡检告警 | 可选 Server酱适配器只在整轮异常时发送；发送失败不影响交易主流程 |

策略只负责计算决策，不发请求、不写数据库。巡检流程负责连接策略、订单执行和持久化。

## 3. 一轮巡检

1. 校验 15 分钟时段，然后先恢复未完成订单；不确定的订单先查询，不重复提交。
2. 并行读取交易所仓位、标的资格和全市场最新价快照；标的资格由 Binance `exchangeInfo` 的 `quoteAsset`、`marginAsset`、`contractType`、`status`、`underlyingType` 和 `underlyingSubType` 字段筛选，合约目录由网关缓存。
3. 将仓位与本地状态及活动订单的预期成交范围核对；无法解释的仓位状态使本轮停止。
4. 按已有持仓优先、新开仓或全平后重开其次处理候选标的；同一优先级内按标的代码排序。每个标的使用全市场快照中对应的最新价。行情只调用一次不带 `symbol` 的 `/fapi/v2/ticker/price`（权重 2）；各标的更新时间可能不同，不读取 K 线或单独请求标记价格。
5. 按交易所数量规则生成订单，买入还检查最小名义价值；账户余额和保证金是否足够由 Binance 在提交时判断。
6. 先保存订单意图，再提交市价单。
7. 查询并确认订单及成交后，按实际成交更新仓位状态。
8. 策略处理结束后读取一次 Binance 账户 `totalMarginBalance` 并写入本地权益快照，供只读看板展示，不参与策略决策。

每轮每个标的最多执行一个止盈或补仓动作。全平订单终态只有部分成交时，剩余仓位进入 `CLOSING`，后续巡检继续尝试全平；确认全平后，若标的仍合格，则在同轮提交重开 T1。若 Binance 拒绝或结果暂时未知，记录原因并由后续巡检按订单状态处理。

## 4. 策略状态

每个标的保存当前 Tier、持仓数量、持仓均价、补仓锚点、止盈批次和生命周期。

| 状态 | 止盈 | 下跌补仓 |
| --- | --- | --- |
| T1 | 最新价收益率达到 10%：全平并开启新周期 | 最新价 ≤ T1 入场价 50%：买入 20 USDT，进入 T2 |
| T2 / T2.1 | T2 达到 20%：卖出初始 T2 仓位一半；T2 或 T2.1 达到 50%：全平并重开 10 USDT T1 | 最新价 ≤ T2 加仓价 50%：买入 60 USDT，进入 T3 |
| T3 / T3.1 / T3.2 | 达到 20%：卖出 T3 初始仓位的 1/3；达到 50%：累计卖出 2/3；达到 100%：全平并重开 10 USDT T1 | 最新价 ≤ `P_writeoff = 5 USDT / Q_T3`：市价全平并重开 10 USDT T1 |

止盈按本轮达到的最高阈值处理，不逐轮补做已跨过的低档：T2 若从低于 20% 直接到达 50%，直接全平；T3 若直接达到 50% 但未到 100%，一次卖出 T3 初始仓位累计的 2/3 并进入 T3.2；若直接达到 100%，全平。已经处于 T3.1 时，达到 50% 再卖出 T3 初始仓位的 1/3，达到 100% 则全平。层级和批次只在对应成交确认后更新；每轮每标的只执行一个止盈或补仓动作。

## 5. 订单与状态保存

SQLite 保留执行闭环所需的记录：

- `symbol_states`：当前标的状态和策略批次。
- `order_intents`：动作、累计卖出目标、下单数量和执行状态；`intent_id` 同时作为 Binance 客户端订单 ID。全平已确认但成交明细待补录时，保存确认时间，以便看板只影响对应日期的统计。升级前的旧记录没有确认时间，会保守地保持统计提示，直到成交明细补录。买入预算只用于规划下单数量，不重复保存在意图记录中。
- `trade_fills`：交易所确认的成交明细；订单终态保存在 `order_intents`。
- `account_equity_snapshots`：每轮策略处理结束后读取的账户权益、未实现盈亏、可用余额和持仓总价值，只供看板展示。
- `latest_symbol_prices`、`dashboard_issues`：看板需要的最近价格和未解决异常，不参与策略决策。

数据库 schema v24 支持从 v21、v22、v23 顺序升级。`trade_fills_by_side_symbol_pnl` 覆盖看板的标的收益排行查询；看板 Tailwind 样式在发布前编译成本地静态 CSS，不依赖外部 CDN。

本轮仓位只在内存中用于核对本系统管理的持仓；策略下单准入不读取账户资产或保证金快照。账户权益采集失败只记日志，不阻断本轮交易。

买入前按标的首次设置杠杆，依次尝试 10x、5x、3x；仅 Binance `-4028` 杠杆无效错误会触发下一档。成功档位按标的在进程内缓存；三档均不支持的结果只在当前 15 分钟批次缓存，下批会重试。其他接口错误直接使该标的本次买入失败，批次继续处理其他标的。平仓不设置杠杆，也不修改保证金模式。

市价订单串行提交，本进程用滚动窗口限制下单请求：10 秒最多 299 笔、60 秒最多 1199 笔；达到任一上限时等待对应窗口内最早的请求过期。订单次数按账户计数。REST 权重按公网 IP 计数；程序读取 Binance 响应中的 `X-MBX-USED-WEIGHT-1M`，达到本地阈值 1800 后，在下一次请求前等待 60 秒；收到 HTTP 429 时按 `Retry-After` 等待，若缺失或无效则等待 60 秒。`/fapi/v2/ticker/price` 的响应头不准确，因此忽略。权重和订单计数都保存在进程内，重启后清空。

订单流程固定为：买入时先确认杠杆 → 保存意图 → 提交订单 → 查询订单与成交 → 按实际成交更新状态。提交结果不确定时先查证，不直接再次下单。订单未终态时保留为活动订单；全平订单终态仅部分成交时，按实际成交更新仓位并标记剩余仓位待全平。

数量按 `MARKET_LOT_SIZE` 的 `minQty` 起点和 `stepSize` 向下对齐。买入按本轮最新价估算并检查 `MIN_NOTIONAL`，Binance 对市价买单使用标记价进行最终校验。分批止盈低于门槛时按现有 PRD 规则合并全平；全平卖单使用 `reduceOnly`，无需满足最小名义价值，仍须满足数量规则。不得向上增加买入金额或卖出超过实际持仓。

## 6. 标的池与下单结果

标的资格由 Binance `exchangeInfo` 实时定义：仅纳入 USDT 报价和保证金、`PERPETUAL`、`TRADING`，且 `underlyingType` 为 `COIN` 或 `INDEX`，或 `underlyingSubType` 包含 `RWA` 的合约。新符合条件的合约在下一次成功刷新目录后自动纳入；失去资格的合约不再新开、补仓或重开，但已有仓位仍继续巡检和退出。

本系统不做账户余额、维持保证金率或账户模式的开仓前审批。程序先持久化订单意图，再提交 Binance；交易所拒单时保留终态并记录拒绝原因，结果未知时保留订单状态并通过客户端订单 ID 查询，不能直接重复下单。

启动时刷新 Binance `exchangeInfo`，成功结果在网关内缓存 15 分钟；缓存过期后刷新失败时不使用过期目录。每个 15 分钟批次先恢复未完成订单，再读取仓位、标的资格和全市场最新价快照。单笔订单查询不确定时将该标的保留为 `UNKNOWN` 并跳过它，其他标的可继续；持仓、合约目录或最新价快照任一整批数据无法读取时，本轮不进入策略处理。全市场价格响应缺少某个候选标的时，只跳过该标的；单个标的规则或下单规划失败时记录异常并继续处理其他标的。

## 7. 必要状态与对账边界

这套策略不需要复杂的业务状态机，但不能完全无状态。SQLite 保存每个标的的当前 Tier、持仓数量与均价、当前 Tier 的入场锚点和初始数量、已完成止盈批次，以及当前仓位是否已确认全平。累计已卖数量由 Tier 初始数量减当前持仓数量计算，不重复保存；已完成批次仍需单独保存，因为数量步长对齐和部分成交会让批次完成状态无法只靠持仓比例判断。T2/T3 的跨档止盈和全平后重开都依赖这些信息。

订单执行状态与策略状态分开保存。订单意图保存动作、目标、提交数量和执行状态；`intent_id` 同时作为客户端订单 ID，实际成交数量由成交明细计算。提交前保存意图和请求数量；超时或重启后用该 ID 查询，确认成交后才更新策略状态。必须保留“结果未知时不重复下单”和“按实际成交更新仓位”这两条规则。

每轮运行结果写入常规运行日志，不另建持久化 review-run 记录；订单记录、成交明细和标的状态已经保存执行所需事实，不再重复写一份状态事件历史。市价单提交时记录标的、方向和数量；`httpx` 的 INFO 请求日志关闭，避免 URL 中的 SendKey 和签名写入日志，告警和错误日志仍保留。

交易所仓位只在本轮内存中用于持仓核对；策略执行不获取账户风险快照。SQLite 保存策略状态、订单状态、已确认成交明细和账户权益采样。全平确认后先原子更新仓位及订单状态，重开后补录成交明细；其他订单将成交、仓位状态和订单终态写入同一事务。不重复保存可从它们推导的执行汇总。标的资格和合约规则只在进程内缓存，不持久化。

标的生命周期包括 `IDLE`、`OPEN`、`CLOSING`、`REOPEN_PENDING`。`CLOSING` 表示全平单终态仅部分成交，保留剩余仓位并在后续巡检继续全平；这个状态复用现有生命周期字段。若完整 `exchangeInfo` 表明合约进入交割/结算状态或已移除，且 Binance 持仓为零、没有未完成订单，批次加载时将本地策略状态重置为 `IDLE` 并跳过该合约；交割/结算期间仍有交易所仓位时保留原状态并跳过策略决策，无法由活动订单解释的数量差异仍会停止批次。这里不新增退市状态，也不把币安结算盈亏或费用写入 `trade_fills`，因此本地收益汇总仅代表策略订单的成交流水。

每轮读取交易所仓位，并核对本系统管理的标的和未完成订单。未知下单结果只阻塞对应标的；仓位数量不一致或发现没有本地状态的非零仓位时，当前实现会让本轮整批失败。由于无法判断未知仓位是否属于策略，运行账户实际上必须专用。

当前只接入可选的 Server酱整轮失败告警；止盈/补仓推送、日报、账户风险监控、历史巡检报表和数据库备份工具不属于精简交易闭环。账户权益曲线由本地快照生成，不提供实时账户查询。执行所需的本地状态、未完成订单恢复和基础仓位核对仍需保留。
