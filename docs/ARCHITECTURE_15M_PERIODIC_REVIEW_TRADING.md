# 15 分钟定时交易系统：精简架构

本文只描述 PRD 所需的最小系统：一个常驻进程，每 15 分钟读取账户和行情，按固定策略决策，执行订单并保存状态。

## 1. 总体结构

```text
15 分钟调度器
      │
      ▼
巡检流程 ─── 策略规则
   │              │
   ├── 交易所 REST 接口
   │      ├── 仓位、价格、合约规则
   │      └── 市价下单、订单和成交查询
   │
   └── SQLite
          ├── 标的状态
          ├── 订单意图
          ├── 成交记录
          └── 账户快照

可选：告警与日报
```

部署为单进程、单账户、单实例。程序以 REST 轮询为主，状态保存在本机 SQLite。

## 2. 模块

| 模块 | 工作内容 |
| --- | --- |
| 调度器 | 在每根 15 分钟 K 线收盘后约 4 秒启动一轮巡检；标的目录启动时加载，之后每日刷新 |
| 巡检流程 | 获取账户快照，读取本地状态，逐个标的调用策略并处理结果 |
| 策略规则 | 根据 Tier、收益率、批次状态和标的资格，返回一个动作或持有 |
| 交易所接口 | 获取持仓、标记价格和交易规则；提交市价单；查询订单与成交 |
| SQLite | 保存标的状态、订单意图、成交记录和账户快照 |
| 通知与日报 | 策略和账务主流程稳定后再接入，不影响订单状态更新 |

策略只负责计算决策，不发请求、不写数据库。巡检流程负责连接策略、订单执行和持久化。

## 3. 一轮巡检

1. 读取交易所仓位、账户风险数据和合约规则；任何必需数据缺失时，本轮不增加仓位。
2. 将交易所仓位与本地状态核对，先处理上轮未确认订单。
3. 对每个已纳管标的读取本轮 15 分钟 K 线收盘价来判断策略；实时标记价格用于下单数量和账户风控估算。
4. 策略生成本轮动作；优先止盈，其次补仓，最后开仓或重开。
5. 检查数量步长、最小名义价值、账户预算和仓位上限。
6. 先保存订单意图，再提交市价单。
7. 查询并确认订单及成交后，按实际成交更新仓位状态；保存账户快照。

每轮每个标的最多执行一个止盈或补仓动作。全平成交确认后，若标的仍合格，则在同轮重新检查风控并重开 T1；确认失败或重开未获批准时，留到后续轮次处理。

## 4. 策略状态

每个标的保存当前 Tier、持仓数量、持仓均价、补仓锚点、止盈批次和生命周期。

| 状态 | 止盈 | 下跌补仓 |
| --- | --- | --- |
| T1 | 收盘收益率达到 10%：全平并开启新周期 | 收盘价 ≤ T1 入场价 50%：买入 20 USDT，进入 T2 |
| T2 / T2.1 | T2 达到 20%：卖出初始 T2 仓位一半；T2 或 T2.1 达到 50%：全平并重开 10 USDT T1 | 收盘价 ≤ T2 加仓价 50%：买入 60 USDT，进入 T3 |
| T3 / T3.1 / T3.2 | 达到 20%：卖出 T3 初始仓位的 1/3；达到 50%：累计卖出 2/3；达到 100%：全平并重开 10 USDT T1 | 收盘价 ≤ `P_writeoff = 5 USDT / Q_T3`：市价全平并重开 10 USDT T1 |

止盈按本轮达到的最高阈值处理，不逐轮补做已跨过的低档：T2 若从低于 20% 直接到达 50%，直接全平；T3 若直接达到 50% 但未到 100%，一次卖出 T3 初始仓位累计的 2/3 并进入 T3.2；若直接达到 100%，全平。已经处于 T3.1 时，达到 50% 再卖出 T3 初始仓位的 1/3，达到 100% 则全平。层级和批次只在对应成交确认后更新；每轮每标的只执行一个止盈或补仓动作。

## 5. 订单与状态保存

SQLite 只保留执行闭环所需的几类记录：

- `symbols_state`：当前标的状态和策略批次。
- `order_intents`：动作、目标数量、唯一业务键、客户端订单 ID 和执行状态。
- `trade_history`：交易所确认的成交、手续费及已实现盈亏。
- `account_snapshots`：账户权益、余额和保证金数据。

订单流程固定为：保存意图 → 提交订单 → 查询订单与成交 → 按实际成交更新状态。提交结果不确定时先查证，不直接再次下单。部分成交按真实成交数量更新；未成交或未确认的部分继续保留在订单状态中。

数量按交易所 `stepSize` 向下对齐，并检查 `MIN_NOTIONAL`。若拆分止盈单无法满足规则，按 PRD 合并处理；不得向上增加买入金额或卖出超过实际持仓。

## 6. 标的池与风险

标的资格来自 PRD 定义的 USDT-M 永续合约池。非原生加密资产和非交易状态合约不自动纳入。分类来源和风险阈值使用显式配置，不从代码中猜测账户参数。

新增仓位前检查账户余额储备、维持保证金率、持仓模式和当前订单预留。数据过期、账户模式不符、预算不足或状态无法解释时，停止该动作并记录原因。

启动时先恢复未完成订单，再读取最近一次完整持久化的合约快照并刷新 Binance `exchangeInfo`。刷新失败时可用缓存规则继续巡检已有持仓，但禁用开仓、补仓和重开；缺少对应缓存规则时拒绝下单。成功刷新后恢复正常准入；没有可用快照时保持启动失败。

## 7. 实现顺序

1. 完成并确认 T1/T2/T3 的纯策略规则。
2. 用 SQLite 保存标的状态和订单意图。
3. 接上交易所 REST 查询、下单和成交确认。
4. 加入标的池刷新、15 分钟调度及每轮结果日志。
5. 主闭环稳定后，再接入收入流水、日报和通知。

参数中尚未给定的保证金上限、USDT 储备和滑点缓冲由配置提供，不在架构中预设账户数值。运行账户和交易环境由项目负责人另行决定。
