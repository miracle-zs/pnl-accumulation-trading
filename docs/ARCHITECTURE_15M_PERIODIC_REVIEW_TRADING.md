# 15 分钟定时交易系统：精简架构

本文只描述 PRD 所需的最小系统：一个常驻进程，每 15 分钟读取账户和行情，按固定策略决策，执行订单并保存状态。

## 1. 总体结构

```text
15 分钟调度器
      │
      ▼
巡检流程 ─── 策略规则
   │              │
   ├── 交易所 REST 接口
   │      ├── 仓位、价格、合约规则
   │      └── 市价下单、订单和成交查询
   │
   └── SQLite
          ├── 标的状态
          ├── 订单意图与执行回执
          ├── 已确认成交
          └── 巡检轮转游标

可选：告警与日报
```

部署为单进程、单账户、单实例。程序以 REST 轮询为主，状态保存在本机 SQLite。

## 2. 模块

| 模块 | 工作内容 |
| --- | --- |
| 调度器 | 在每根 15 分钟 K 线收盘后约 4 秒启动一轮巡检；标的目录启动时加载，之后每日刷新 |
| 巡检流程 | 获取本轮仓位和行情，读取本地状态，逐个标的调用策略并处理结果 |
| 策略规则 | 根据 Tier、收益率、批次状态和标的资格，返回一个动作或持有 |
| 交易所接口 | 获取持仓、15 分钟 K 线收盘价和交易规则；提交市价单；查询订单与成交 |
| SQLite | 保存标的状态、订单执行事实和巡检轮转位置 |
| 通知与日报 | 策略和账务主流程稳定后再接入，不影响订单状态更新 |

策略只负责计算决策，不发请求、不写数据库。巡检流程负责连接策略、订单执行和持久化。

## 3. 一轮巡检

1. 读取交易所仓位和合约规则；必需的策略或市场数据缺失时，不生成该标的订单。
2. 将交易所仓位与本地状态核对，先处理上轮未确认订单。
3. 对每个已纳管标的读取本轮 15 分钟 K 线收盘价，用于策略判断和下单数量换算；不单独请求标记价格或账户资产快照。
4. 策略生成本轮动作；优先止盈，其次补仓，最后开仓或重开。
5. 按交易所数量步长和最小名义价值生成订单；账户余额和保证金是否足够由 Binance 在提交时判断。
6. 先保存订单意图，再提交市价单。
7. 查询并确认订单及成交后，按实际成交更新仓位状态。

每轮每个标的最多执行一个止盈或补仓动作。全平成交确认后，若标的仍合格，则在同轮提交重开 T1；若 Binance 拒绝或结果暂时未知，记录原因并由后续巡检按订单状态处理。

## 4. 策略状态

每个标的保存当前 Tier、持仓数量、持仓均价、补仓锚点、止盈批次和生命周期。

| 状态 | 止盈 | 下跌补仓 |
| --- | --- | --- |
| T1 | 收盘收益率达到 10%：全平并开启新周期 | 收盘价 ≤ T1 入场价 50%：买入 20 USDT，进入 T2 |
| T2 / T2.1 | T2 达到 20%：卖出初始 T2 仓位一半；T2 或 T2.1 达到 50%：全平并重开 10 USDT T1 | 收盘价 ≤ T2 加仓价 50%：买入 60 USDT，进入 T3 |
| T3 / T3.1 / T3.2 | 达到 20%：卖出 T3 初始仓位的 1/3；达到 50%：累计卖出 2/3；达到 100%：全平并重开 10 USDT T1 | 收盘价 ≤ `P_writeoff = 5 USDT / Q_T3`：市价全平并重开 10 USDT T1 |

止盈按本轮达到的最高阈值处理，不逐轮补做已跨过的低档：T2 若从低于 20% 直接到达 50%，直接全平；T3 若直接达到 50% 但未到 100%，一次卖出 T3 初始仓位累计的 2/3 并进入 T3.2；若直接达到 100%，全平。已经处于 T3.1 时，达到 50% 再卖出 T3 初始仓位的 1/3，达到 100% 则全平。层级和批次只在对应成交确认后更新；每轮每标的只执行一个止盈或补仓动作。

## 5. 订单与状态保存

SQLite 保留执行闭环和启动所需的记录：

- `symbol_states`：当前标的状态和策略批次。
- `order_intents` 与 `order_attempts`：动作、目标数量、唯一业务键、客户端订单 ID 和执行状态。
- `execution_receipts` 与 `trade_fills`：交易所确认的订单结果和成交明细。
- `review_rotation_cursors`：保存每类巡检候选的轮转位置。

本轮仓位只在内存中用于核对本系统管理的持仓；策略下单准入不读取账户资产或保证金快照。

订单流程固定为：保存意图 → 提交订单 → 查询订单与成交 → 按实际成交更新状态。提交结果不确定时先查证，不直接再次下单。部分成交按真实成交数量更新；未成交或未确认的部分继续保留在订单状态中。

数量按交易所 `stepSize` 向下对齐，并检查 `MIN_NOTIONAL`。若拆分止盈单无法满足规则，按 PRD 合并处理；不得向上增加买入金额或卖出超过实际持仓。

## 6. 标的池与下单结果

标的资格来自 PRD 定义的 USDT-M 永续合约候选池。非原生加密资产、非交易状态合约和未审核的新合约不自动纳入。维护者审核后将资产写入分类文件，应用重启时加载。

本系统不做账户余额、维持保证金率或账户模式的开仓前审批。程序先持久化订单意图，再提交 Binance；交易所拒单时保留终态并记录拒绝原因，结果未知时保留订单状态并通过客户端订单 ID 查询，不能直接重复下单。

启动时先恢复未完成订单，再从 Binance `exchangeInfo` 获取当前合约规则和标的资格。获取失败时本轮直接失败，不使用上次运行遗留的规则继续交易。网关在进程内缓存成功结果 24 小时，减少正常巡检的重复请求；缓存过期后刷新失败仍按失败处理。

## 7. 实现顺序

1. 完成并确认 T1/T2/T3 的纯策略规则。
2. 用 SQLite 保存标的状态和订单意图。
3. 接上交易所 REST 查询、下单和成交确认。
4. 加入标的池刷新、15 分钟调度及每轮结果日志。
5. 主闭环稳定后，再接入收入流水、日报和通知。

运行账户和交易环境由项目负责人另行决定。账户资金是否足以执行由 Binance 下单结果反馈；运行配置不要求账户保证金上限、USDT 储备或滑点缓冲参数。

## 8. 必要状态与对账边界

这套策略不需要复杂的业务状态机，但不能完全无状态。SQLite 至少要保存每个标的的当前 Tier、持仓数量与均价、当前 Tier 的入场锚点和初始数量、累计已卖数量或已完成批次，以及当前仓位是否已确认全平。T2/T3 的跨档止盈和全平后重开都依赖这些信息。

订单执行状态与策略状态分开保存。最小订单记录包含动作、数量、客户端订单 ID、已确认成交量和结果是否确定。订单提交前先保存记录；超时或重启后先用客户端订单 ID 查询，确认成交后才更新策略状态。状态名称可以合并，不能省掉“结果未知时不重复下单”和“按实际成交更新仓位”这两条规则。

每轮运行结果写入常规运行日志，不另建持久化 review-run 记录；成交回执、订单记录和标的状态已经保存执行所需事实，不再重复写一份状态事件历史。

交易所仓位只在本轮内存中用于持仓核对；策略执行不获取账户风险快照。SQLite 只保存策略状态、未完成订单、已确认回执与成交，以及巡检轮转位置。标的资格和合约规则只在进程内缓存，不持久化。

当前代码只保留实际交易流程会进入的 `IDLE`、`OPEN`、`REOPEN_PENDING` 三种标的生命周期。隔离、退市结算和永久退役状态没有实际写入流程，先不保留占位枚举；实现对应的退市处置流程时再加入所需状态。

每轮读取交易所仓位，并核对本系统管理的标的和未完成订单。发现仓位数量不一致、未识别订单或未知下单结果时，暂停受影响标的的后续动作并先查清。若账户同时用于手工交易，必须先确定哪些仓位归本系统管理；当前实现把未知持仓或挂单视为整轮错误，因此实际上要求使用专用账户。

以下能力不属于精简交易闭环：日报和 Webhook 通知、账户风险监控、历史报表、数据库备份工具。执行所需的本地状态、未完成订单恢复和基础仓位核对仍需保留。
