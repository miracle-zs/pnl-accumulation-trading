**Version**: 1.0.0

**Target Platform**: Binance USDT-M Futures (币安永续合约)  
**Author**: Antigravity Quant Team  

---

## 1. 项目背景与设计哲学 (Background & Philosophy)

### 1.1 背景痛点
传统的“盘中限价单（Limit Order TP）+ 平完秒开”网格架构，在实盘落地上面临三大工程与市场力学瓶颈：
1. **连接与状态机极重**：必须维持 7×24 小时高频 WebSocket（User Data Stream）长连接，监听每一笔成交。一旦网络抖动、掉线重连或服务器重启，容易出现挂单脱轨、重复挂单或漏单；
2. **交易所规则硬约束**：币安对单个账户有最大挂单数限制（Max Open Orders 200 个），多标的（50~100 个币）同时运行很容易因达到挂单上限而被拒绝下单；
3. **脉冲暴拉时的追高陷阱**：山寨币短时暴涨（如 5 秒内暴拉 +25%）打穿 +10% 限价单时，程序收到成交推送时市价往往已飙至高位，此时“原价秒开”根本无法成交，市价追单则面临巨大追高滑点，直接挂在山顶。

### 1.2 15 分钟定时统计的设计哲学
本方案采用**“离散时间采样（Discrete-Time Sampling）+ REST 周期轮询 + 最小持久状态”**的设计：
* **工程降维**：不使用 WebSocket 订单监听或策略限价挂单；每 15 分钟通过 REST 巡检，SQLite 只保留策略状态、订单意图与成交明细；
* **最新价决策**：每 15 分钟整刻启动一次巡检，读取 Binance 全市场最新价快照，用每个标的对应的最新价判断策略动作并规划市价单；实际成交价格由交易所执行决定。

## 3. 核心业务流程与仓位状态机 (State Machine & Logic)

### 3.1 标的池定义：币安活跃 COIN / INDEX / RWA 永续合约

系统从 Binance `GET /fapi/v1/exchangeInfo` 动态构建标的池，只纳入同时满足以下条件的合约：

* `quoteAsset = USDT` 且 `marginAsset = USDT`；
* `contractType = PERPETUAL` 且 `status = TRADING`；
* `underlyingType` 为 `COIN` 或 `INDEX`，或 `underlyingSubType` 包含 `RWA`。

以上字段用于排除股票、商品、外汇等非目标合约及预上市、非交易状态合约；`INDEX` 和 `RWA` 子类型纳入标的池。按 2026-10-27 查询，符合条件的标的为 **522 个**；该数量随币安上新、下架和状态变化而变化。

符合条件的新合约会在下一次成功刷新 `exchangeInfo` 后自动进入标的池，并按策略决定是否开立 10 USDT Tier 1 底仓；不再维护人工资产分类名单。

合约失去新开资格后，不再开新仓、补仓或重开；已有仓位仍按策略管理和退出。币安按公告时间自动结算未平仓位，系统不下交割单。若本地仍记有持仓，但币安持仓快照已为零且没有未完成订单，系统自动将本地策略状态清为 `IDLE`；无法解释的仓位数量差异仍会停止整轮。

#### 资金规模与账户保证金测算（按当前 522 个标的估算）
* **单币底仓参数**：名义价值 10 USDT，目标杠杆 10x。每个标的首次买入前依次尝试 10x、5x、3x；仅币安返回杠杆无效错误（`-4028`）时尝试下一档。选定杠杆在本进程中按标的缓存，后续补仓和重开沿用。
* **初始底仓估算**：522 个标的全部开立 T1 时，名义总额 5,220 USDT；全部使用 10x 时初始保证金估算为 522 USDT，全部使用 5x 时约 1,044 USDT，全部使用 3x 时约 1,740 USDT。实际结果按各标的选中的杠杆而不同，且部分标的可能受最小下单数量或名义价值限制而无法开仓。
* 该初始保证金估算仅作参考，不是实盘安全本金或强平结论。真实保证金取决于 Binance 合约风险限额、维持保证金、资金费、滑点和账户持仓。本系统不在下单前读取账户快照做保证金准入；买单由 Binance 接受或拒绝，拒单原因写入运行日志。若 10x、5x、3x 均被明确拒绝，该标的本次买入跳过；认证、限流、网络等其他错误不触发降档，并按单标的异常处理。

### 3.2 仓位层级（Tier）状态流转与执行规则

系统严格执行 **3-Tier 网格 + 循环贬值复活机制**，全系统**零挂单**，所有止盈、补仓均由每 15 分钟整刻的最新价巡检触发市价单执行：

```

| Tier 1 (首仓底仓)                                                                                 |
| - 名义买入: 10 USDT (记录入场价 entry_t1)                                                          |
| - 最新价浮盈 >= 10%: 市价全平，立刻在当前价格重新以 10 USDT 开仓 Tier 1 (完成一轮资金循环)     |

| - 止盈检查 (基于持仓均价 avg_price):                                                              |
|   * 浮盈 >= 20%: 平掉 50% 仓位 (初始 T2 仓位的一半)，进入 Tier 2.1 状态                           |

+---------------------------------------------------------------------------------------------------+

                         v                                                 |
+------------------------------------------------------------------+       |
```

**止盈跨档规则**：每轮巡检按本轮收益率达到的最高止盈档处理，不逐轮补做已经跨过的低档。T2/T2.1 在浮盈达到 50% 时直接全平并重开 T1，即使此前尚未触发 20% 的 T2 第一批止盈。T3 在浮盈达到 100% 时全平并重开 T1；达到 50% 但未达到 100% 时，一次平掉 T3 初始仓位累计的 2/3 并进入 T3.2；达到 20% 但未达到 50% 时，平掉 T3 初始仓位的 1/3 并进入 T3.1。若已处于 T3.1，达到 50% 时再平掉 T3 初始仓位的 1/3；达到 100% 时全平并重开 T1。

### 3.3 全系统执行模式：15 分钟 REST 市价轮询（不挂限价单）

用户最终确认采用**整刻巡检、按最新价决策、不挂限价单的方案**：
* **不提交限价单**：策略不在交易所保留等待触发的限价挂单。
* **每轮在 00、15、30、45 分的第 0 秒触发**：读取 Binance 返回的全市场最新价，用对应标的价格计算收益并判断策略动作。每个标的的最新价更新时间可能不同，快照也不能保证等于上一根 15 分钟 K 线的收盘价。
  * 止盈平仓：最新价达到策略阈值时市价平仓；
  * 平仓后重开：确认全平后，立即市价开 10U；
  * DCA 跌破补仓：最新价 $\le$ 上一档价格的 50% 时，市价买入 20U / 60U；
  * 利润反哺注销：最新价 $\le P_{writeoff}$ 时，市价全平注销死仓并重开 10U T1。
* **订单结果仍需确认**：市价单提交后，通过 REST 查询订单和成交；结果未知时按客户端订单 ID 查询，不重复提交。SQLite 保存必要的策略状态和未完成订单，用于按实际成交更新仓位并在重启后恢复。
* **执行方式**：系统不使用 WebSocket，也不保留策略限价挂单。市价订单串行提交；本进程按滚动窗口限制下单请求：10 秒最多 299 笔、60 秒最多 1199 笔，达到上限时等待窗口内最早的请求过期。订单次数按账户统计，REST 请求权重按公网 IP 统计；同一 IP 上的其他项目也会占用权重。程序观察 Binance 返回的 `X-MBX-USED-WEIGHT-1M`，达到本地阈值 1800 后，在下一次请求前等待 60 秒；收到 HTTP 429 时按 `Retry-After` 等待，若缺失或无效则等待 60 秒。`/fapi/v2/ticker/price` 的该响应头不准确，程序忽略该接口的响应值。两类本地计数在进程内维护，重启后清空。每轮执行时间取决于候选标的数量和 REST 请求耗时，不承诺固定在 2 秒内完成。

## 4. 15 分钟巡检调度执行细节 (Review Engine Execution)

### 4.1 触发时序
* 调度器使用 UTC，在每小时的 `00`、`15`、`30`、`45` 分第 0 秒启动巡检；
* 每轮只执行一次最新价快照决策，不补跑超过调度宽限期的旧巡检轮。

### 4.2 每轮巡检要求
1. 先按客户端订单 ID 恢复未完成订单；结果不确定时不重复提交，相关标的保持阻塞。
2. 每轮读取一次交易所持仓，并读取已审核标的资格；将本地状态与交易所持仓及未完成订单的预期数量范围核对。退市合约在币安持仓归零且没有未完成订单后自动清除本地策略状态；其他无法解释的仓位差异或无本地状态的非零仓位会停止本轮。
3. 与持仓和标的资格快照并行，一次读取 Binance 全市场最新价；按持仓优先、开仓其次的顺序使用快照中对应标的价格，不额外读取标记价或 K 线。
4. 每个标的每轮最多执行一个止盈或补仓动作。全平订单终态只有部分成交时，将剩余仓位记为 `CLOSING`，后续巡检继续尝试全平，不再按收益率或补仓阈值重新决策。币安确认全平成交后，若标的仍符合开仓条件，则立即在同轮重开 T1，不等待逐笔成交明细。平仓明细在后续补录；未确认全平时不重开。
5. 买入动作在保存订单意图前，按 10x、5x、3x 顺序尝试设置杠杆；已成功设置的杠杆按标的在进程内缓存。随后按交易所数量规则对齐并估算最小名义价值，保存订单意图，再提交市价单。若三档杠杆均被币安明确拒绝，则跳过该标的买入。只有交易所成交得到确认后，才按实际成交更新仓位状态和成交流水。
6. 全市场最新价、持仓或标的资格快照读取失败，以及无法解释的持仓差异，会停止本轮；单个标的缺少最新价、规则或下单失败时记录异常并继续处理其他标的。

## 5. 本地持久化要求

使用单机 SQLite 保存精简闭环必需的执行事实：

* `symbol_states` 保存标的当前 Tier、数量、均价、当前 Tier 的入场数据、止盈批次和生命周期；累计已卖数量由 Tier 入场数量减当前数量得出，不重复保存。
* `order_intents` 保存动作、累计卖出目标、请求数量和执行状态；`intent_id` 同时作为 Binance 客户端订单 ID。订单意图和请求数量必须在提交前保存。
* `trade_fills` 保存 Binance 已确认的策略订单成交明细。全平订单确认成交后，先在同一事务中更新仓位状态并结束订单意图，再于重开后补录平仓明细；补录失败会在后续巡检重试。其他订单在同一事务中写入成交、更新标的状态并结束订单意图。币安退市结算产生的盈亏和费用不属于策略订单成交，不计入本地成交账本及其收益汇总。
* `account_equity_snapshots` 保存每轮策略处理结束后从 Binance 获取的账户权益、未实现盈亏、可用余额和持仓总价值，仅供看板展示；不用于下单准入或风险判断。整体实际杠杆为持仓总价值除以账户权益，权益不大于零时不计算。权益曲线提供 24 小时、7 天和 30 天视图。
* `latest_symbol_prices` 保存当前持仓最近一轮的巡检价格，仅供看板估算名义价值和浮动盈亏；`dashboard_issues` 保存当前未解决的标的异常及整轮异常，仅供看板展示。

不保存每轮巡检明细，也不自动重建持仓状态。数据库使用 schema v24；支持 v21、v22、v23 按顺序升级，其他已有版本不自动迁移。若本地状态缺失而交易所仍有策略仓位或未决订单，负责人必须先恢复或人工核对后再启动。表结构以《15 分钟定时交易系统：精简架构》为准。

## 6. 异常与边缘场景防范 (Edge Cases & Safety Rules)

### 6.1 币安最小名义价值限制（MIN_NOTIONAL）
* **买入**：按合约 `exchangeInfo` 中的最小名义价值和最新价进行估算，不同合约的门槛可能不同。Binance 对市价买单使用标记价进行最终校验，拒单时记录异常。
* **分批止盈**：沿用当前策略规则，若按最新价估算的分批名义价值低于该合约门槛，系统合并为整仓平仓。这是策略设定；币安对 `reduceOnly` 订单不强制执行最小名义价值限制。
* **全平**：市价卖单使用 `reduceOnly`，因此无需满足最小名义价值，仍须满足合约的市价数量规则。交易所确认全平后再开仓。

### 6.2 市价单数量对齐（MARKET_LOT_SIZE）
* 下单使用 `/fapi/v1/exchangeInfo` 中的 `minQty`、`maxQty` 和 `stepSize`；合约目录由网关进程内缓存，不逐笔下单刷新。数量从 `minQty` 起按 `stepSize` 向下对齐，且不得超过 `maxQty`，严禁向上取整导致超额下单或平仓。

### 6.3 网络超时与 API 限流（429 频控防范）
* 每轮只读取一次账户持仓；策略处理结束后额外读取一次账户权益（`totalMarginBalance`，仅用于看板，Binance API 权重 5）；合约目录在进程内缓存 15 分钟；每轮通过一次不带 `symbol` 的 `/fapi/v2/ticker/price` 读取全市场最新价（权重 2），不逐标的请求 K 线，也不额外请求标记价；该接口按标的返回最新价及其时间，价格采样不保证发生在完全相同的毫秒；
* 只读 GET 遇到网络错误、服务端错误或 429 时，指数退避重试最多 3 次；市价下单 POST 不自动重试，结果不确定时按客户端订单 ID 查询，确认前不重复提交。

### 6.4 重启恢复与本地状态丢失
* SQLite 状态文件仍在时，每轮策略处理前先按客户端订单 ID 查询未完成订单，再按确认成交更新本地状态；实盘持仓快照用于核对本地状态。
* 不从持仓名义金额推断 Tier 或止盈批次。数据库丢失时，新数据库不包含原策略状态；若账户仍有本系统持仓或未决订单，负责人必须先恢复或人工核对状态，再启动交易服务。
* 当前不迁移旧数据库，也不提供数据库丢失后的自动重建。

## 7. 巡检失败通知

* 配置 `SERVERCHAN_SENDKEY` 后，整轮巡检异常（例如仓位不一致导致本轮停止）会发送 Server酱通知，包含 UTC 巡检时段和安全的错误摘要；单个标的失败仍只记入服务日志。
* Server酱通知发送失败只记日志，不影响交易进程；未配置 SendKey 时交易服务照常运行。
* 同一段连续整轮故障只发送首条提醒，成功完成一轮后重新启用提醒，避免持续故障每 15 分钟重复推送。
* 成交提醒、补仓提醒、每日晨报和保证金熔断通知仍不属于当前闭环。

## 8. 上线里程碑与交付计划 (Roadmap)

1. **Phase 1（精简交易闭环）**：
   * 完成策略判断、SQLite 状态与订单保存、Binance REST 交易接入及 15 分钟巡检调度。
2. **Phase 2（主网运行验收，由项目负责人另行决定）**：
   * 确认账户状态、自动筛选后的标的池和本地状态文件后，由负责人明确决定是否启动主网服务；开发和代码审查过程不自动启动服务或提交订单。
3. **Phase 3（可选扩展）**：
   * 核心交易闭环稳定后，再考虑止盈/补仓推送和每日晨报；它们不作为交易执行的前置条件。整轮失败告警已由可选 Server酱通知覆盖。
