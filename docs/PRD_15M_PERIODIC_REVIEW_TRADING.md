# 产品需求文档 (PRD)：15 分钟定时收益统计自动化交易系统
**Version**: 1.0.0  
**Status**: Ready for Implementation  
**Target Platform**: Binance USDT-M Futures (币安永续合约)  
**Author**: Antigravity Quant Team  

---

## 1. 项目背景与设计哲学 (Background & Philosophy)

### 1.1 背景痛点
传统的“盘中限价单（Limit Order TP）+ 平完秒开”网格架构，在实盘落地上面临三大工程与市场力学瓶颈：
1. **连接与状态机极重**：必须维持 7×24 小时高频 WebSocket（User Data Stream）长连接，监听每一笔成交。一旦网络抖动、掉线重连或服务器重启，容易出现挂单脱轨、重复挂单或漏单；
2. **交易所规则硬约束**：币安对单个账户有最大挂单数限制（Max Open Orders 200 个），多标的（50~100 个币）同时运行很容易因达到挂单上限而被拒绝下单；
3. **脉冲暴拉时的追高陷阱**：山寨币短时暴涨（如 5 秒内暴拉 +25%）打穿 +10% 限价单时，程序收到成交推送时市价往往已飙至高位，此时“原价秒开”根本无法成交，市价追单则面临巨大追高滑点，直接挂在山顶。

### 1.2 15 分钟定时统计的设计哲学
本方案采用**“离散时间采样（Discrete-Time Sampling）+ REST 周期轮询 + 最小持久状态”**的设计：
* **工程降维**：不使用 WebSocket 订单监听或策略限价挂单；每 15 分钟通过 REST 巡检，SQLite 只保留策略状态、订单意图与成交明细；
* **收盘价决策**：只根据已收盘的 15 分钟 K 线判断策略动作，再提交市价单；实际成交价格由交易所执行决定。

## 3. 核心业务流程与仓位状态机 (State Machine & Logic)

### 3.1 标的池定义：全量原生币圈活跃合约标的 (All Native Crypto Universe)

系统标的池明确定义为：**币安 USDT-M 永续合约盘面上，所有存活且处于正常可交易状态（TRADING）的纯原生加密货币（Native Crypto），当前约为 630 个标的**。

#### 1. 严格过滤黑名单规则（彻底排除非加密资产）
系统在每日早 8 点或启动初始化时，调用 `GET /fapi/v1/exchangeInfo` 进行动态扫描，严格剔除以下四类非加密资产：
* **美股 / 港股 / 中概 / 韩股代币 (135+ 个)**：如 `AAPLUSDT`, `TSLAUSDT`, `NVDAUSDT`, `MSFTUSDT`, `BABAUSDT`, `PDDUSDT`, `COINUSDT`, `MSTRUSDT` 等；
* **宏观指数与杠杆 ETF (38+ 个)**：如 `SPYUSDT`, `QQQUSDT`, `TQQQUSDT`, `SQQQUSDT`, `SOXLUSDT`, `UVXYUSDT`, `BITOUSDT` 等；
* **大宗商品 / 外汇 / 稳定币互换 (14+ 个)**：如 `COPPERUSDT` (铜), `NATGASUSDT` (天然气), `USDBRLUSDT` (法币外汇), `USDCUSDT` (稳定币互换), `BTCDOMUSDT` (市占率指数) 等；
* **非正常交易/已下架合约**：`status != 'TRADING'` 的退市合约。

#### 2. 新币发现与人工审核
* 系统每日或启动时扫描 `exchangeInfo`。新发现的合约先标记为待审核，不参与开仓或补仓；
* 维护者确认其为原生加密资产后，将它加入已审核的标的分类文件。重启后系统加载该审核版本；符合正常交易条件的标的从下一轮开始进入策略判断，按策略决定是否开立 10 USDT Tier 1 底仓；
* **退市处置**：币安按公告时间自动结算未平仓位；系统不下交割单。合约进入交割/结算状态，或从成功获取的完整 `exchangeInfo` 列表中消失后，不再参与策略巡检。若本地仍记有持仓，但币安持仓快照已为零且没有未完成订单，系统自动将本地策略状态清为 `IDLE`；结算前仍有仓位时保留状态并等待后续巡检，无法解释的仓位数量差异仍会停止整轮。

#### 3. 资金规模与账户保证金测算（以 630 个原生币为例）
* **单币底仓参数**：名义价值 10 USDT，目标杠杆 10x。每个标的首次买入前依次尝试 10x、5x、3x；仅币安返回杠杆无效错误（`-4028`）时尝试下一档。选定杠杆在本进程中按标的缓存，后续补仓和重开沿用。
* **初始底仓估算**：630 个标的全部开立 T1 时，名义总额 6,300 USDT；全部使用 10x 时初始保证金估算为 630 USDT，全部使用 5x 时约 1,260 USDT，全部使用 3x 时约 2,100 USDT。实际结果按各标的选中的杠杆而不同。
* 该初始保证金估算仅作参考，不是实盘安全本金或强平结论。真实保证金取决于 Binance 合约风险限额、维持保证金、资金费、滑点和账户持仓。本系统不在下单前读取账户快照做保证金准入；买单由 Binance 接受或拒绝，拒单原因写入运行日志。若 10x、5x、3x 均被明确拒绝，该标的本次买入跳过；认证、限流、网络等其他错误不触发降档，并按单标的异常处理。

### 3.2 仓位层级（Tier）状态流转与执行规则

系统严格执行 **3-Tier 网格 + 循环贬值复活机制**，全系统**零挂单**，所有止盈、补仓均由每 15 分钟收盘巡检触发市价单执行：

```
+---------------------------------------------------------------------------------------------------+
| Tier 1 (首仓底仓)                                                                                 |
| - 名义买入: 10 USDT (记录入场价 entry_t1)                                                          |

| - 15m 巡检跌幅触发: 收盘价 <= entry_t1 * 50% (较上一档买入价跌 >= 50%) -> 市价买入 20 USDT 进 T2   |
+---------------------------------------------------------------------------------------------------+

+---------------------------------------------------------------------------------------------------+

| - 止盈检查 (基于持仓均价 avg_price):                                                              |
|   * 浮盈 >= 20%: 平掉 50% 仓位 (初始 T2 仓位的一半)，进入 Tier 2.1 状态                           |

                         v                                                 |
+------------------------------------------------------------------+       |
| Tier 2.1 (半仓观察态，剩余持仓 15U)                              |       |
| - 止盈检查: 较均价浮盈 >= 50% -> 市价全平，重新开 10U 回到 Tier 1 |       |

| - 核心哲学: 坚决不盲目加仓补无底洞，利用大盘已积累的近 1 万刀丰厚现金利润，直接打扫战场！       |
| - 执行动作:                                                                                       |
|   1. 市价全平割肉注销 (Market Close All)，将约 85U 亏损计入利润核销；                             |
```

**止盈跨档规则**：每轮巡检按本轮收益率达到的最高止盈档处理，不逐轮补做已经跨过的低档。T2/T2.1 在浮盈达到 50% 时直接全平并重开 T1，即使此前尚未触发 20% 的 T2 第一批止盈。T3 在浮盈达到 100% 时全平并重开 T1；达到 50% 但未达到 100% 时，一次平掉 T3 初始仓位累计的 2/3 并进入 T3.2；达到 20% 但未达到 50% 时，平掉 T3 初始仓位的 1/3 并进入 T3.1。若已处于 T3.1，达到 50% 时再平掉 T3 初始仓位的 1/3；达到 100% 时全平并重开 T1。

### 3.3 全系统执行模式：15 分钟 REST 市价轮询（不挂限价单）

用户最终确认采用**不挂限价单的方案**：
* **不提交限价单**：策略不在交易所保留等待触发的限价挂单。
* **每轮在 15m 收盘后判定动作**：
  * 止盈平仓：15m 收盘市价平仓；
  * 平仓后重开：15m 收盘市价开 10U；
  * DCA 跌破补仓：15m 收盘若价格 $\le$ 上一档价格的 50%，市价买入 20U / 60U；
  * 利润反哺注销：15m 收盘若现价 $\le P_{writeoff}$，市价全平注销死仓并重开 10U T1。
* **订单结果仍需确认**：市价单提交后，通过 REST 查询订单和成交；结果未知时按客户端订单 ID 查询，不重复提交。SQLite 保存必要的策略状态和未完成订单，用于按实际成交更新仓位并在重启后恢复。
* **执行方式**：系统不使用 WebSocket，也不保留策略限价挂单。市价订单串行提交，间隔至少 200 毫秒，以控制集中开仓的下单频率；每轮执行时间取决于候选标的数量和 REST 请求耗时，不承诺固定在 2 秒内完成。

## 4. 15 分钟巡检调度执行细节 (Review Engine Execution)

### 4.1 触发时序
* 调度器使用 UTC，在每小时的 `00`、`15`、`30`、`45` 分第 5 秒启动巡检；
* 每轮只处理刚收盘的 15 分钟时段，不补跑超过调度宽限期的旧时段。

### 4.2 每轮巡检要求
1. 先按客户端订单 ID 恢复未完成订单；结果不确定时不重复提交，相关标的保持阻塞。
2. 每轮读取一次交易所持仓，并读取已审核标的资格；将本地状态与交易所持仓及未完成订单的预期数量范围核对。退市合约在币安持仓归零且没有未完成订单后自动清除本地策略状态；其他无法解释的仓位差异或无本地状态的非零仓位会停止本轮。
3. 按持仓优先、开仓其次的顺序处理标的。策略只使用该时段 15 分钟 K 线收盘价，不另取标记价。
4. 每个标的每轮最多执行一个止盈或补仓动作。全平成交确认后，若标的仍通过审核且符合开仓条件，则在同轮重开 T1。
5. 买入动作在保存订单意图前，按 10x、5x、3x 顺序尝试设置杠杆；已成功设置的杠杆按标的在进程内缓存。随后按交易所数量规则对齐并估算最小名义价值，保存订单意图，再提交市价单。若三档杠杆均被币安明确拒绝，则跳过该标的买入。只有交易所成交得到确认后，才按实际成交更新仓位状态和成交流水。
6. 单个标的的行情、规则或下单失败只记录异常并继续处理其他标的；持仓或标的资格整批快照失败，以及无法解释的持仓差异，会停止本轮。

## 5. 本地持久化要求

使用单机 SQLite 保存精简闭环必需的执行事实：

* `symbol_states` 保存标的当前 Tier、数量、均价、当前 Tier 的入场数据、止盈批次和生命周期；累计已卖数量由 Tier 入场数量减当前数量得出，不重复保存。
* `order_intents` 保存动作、累计卖出目标、请求数量和执行状态；`intent_id` 同时作为 Binance 客户端订单 ID。订单意图和请求数量必须在提交前保存。
* `trade_fills` 保存 Binance 已确认的策略订单成交明细。确认成交后，在同一事务中写入成交、更新标的状态并结束订单意图。币安退市结算产生的盈亏和费用不属于策略订单成交，不计入本地成交账本及其收益汇总。

账户资产快照、每轮巡检历史和自动重建持仓状态不属于当前闭环。旧数据库不迁移；若本地状态缺失而交易所仍有策略仓位或未决订单，负责人必须先恢复或人工核对后再启动。表结构以《15 分钟定时交易系统：精简架构》为准。

## 6. 异常与边缘场景防范 (Edge Cases & Safety Rules)

### 6.1 币安最小名义价值限制（MIN_NOTIONAL = 5 USDT）
* **规则**：币安合约单笔下单名义价值不得低于 5 USDT；
* **处理方案**：
  * Tier 1 开仓为 10 USDT（高于 5U，正常通过）；
  * Tier 2 分批平仓为 15 USDT（高于 5U，正常通过）；
  * 若按最近 15 分钟收盘价估算的分批平仓名义价值低于 5 USDT，系统合并为整仓平仓。由于不单独请求标记价，本地结果只是估算；Binance 仍按标记价做市价单最终校验，拒单时记录异常，不保证合并单一定通过。

### 6.2 市价单数量对齐（MARKET_LOT_SIZE）
* 下单使用 `/fapi/v1/exchangeInfo` 中的 `minQty`、`maxQty` 和 `stepSize`；合约目录由网关进程内缓存，不逐笔下单刷新。数量从 `minQty` 起按 `stepSize` 向下对齐，且不得超过 `maxQty`，严禁向上取整导致超额下单或平仓。

### 6.3 网络超时与 API 限流（429 频控防范）
* 每轮只读取一次账户持仓；合约目录在进程内缓存 15 分钟；每个进入策略决策的候选标的读取一根 15 分钟 K 线，不额外请求标记价或账户资产快照；
* 只读 GET 遇到网络错误、服务端错误或 429 时，指数退避重试最多 3 次；市价下单 POST 不自动重试，结果不确定时按客户端订单 ID 查询，确认前不重复提交。

### 6.4 重启恢复与本地状态丢失
* SQLite 状态文件仍在时，每轮策略处理前先按客户端订单 ID 查询未完成订单，再按确认成交更新本地状态；实盘持仓快照用于核对本地状态。
* 不从持仓名义金额推断 Tier 或止盈批次。数据库丢失时，新数据库不包含原策略状态；若账户仍有本系统持仓或未决订单，负责人必须先恢复或人工核对状态，再启动交易服务。
* 当前不迁移旧数据库，也不提供数据库丢失后的自动重建。

## 7. 巡检失败通知

* 配置 `SERVERCHAN_SENDKEY` 后，整轮巡检异常（例如仓位不一致导致本轮停止）会发送 Server酱通知，包含 UTC 巡检时段和安全的错误摘要；单个标的失败仍只记入服务日志。
* Server酱通知发送失败只记日志，不影响交易进程；未配置 SendKey 时交易服务照常运行。
* 同一段连续整轮故障只发送首条提醒，成功完成一轮后重新启用提醒，避免持续故障每 15 分钟重复推送。
* 成交提醒、补仓提醒、每日晨报和保证金熔断通知仍不属于当前闭环。

## 8. 上线里程碑与交付计划 (Roadmap)

1. **Phase 1（精简交易闭环）**：
   * 完成策略判断、SQLite 状态与订单保存、Binance REST 交易接入及 15 分钟巡检调度。
2. **Phase 2（主网运行验收，由项目负责人另行决定）**：
   * 确认账户状态、审核后的标的分类和本地状态文件后，由负责人明确决定是否启动主网服务；开发和代码审查过程不自动启动服务或提交订单。
3. **Phase 3（可选扩展）**：
   * 核心交易闭环稳定后，再考虑止盈/补仓推送和每日晨报；它们不作为交易执行的前置条件。整轮失败告警已由可选 Server酱通知覆盖。
